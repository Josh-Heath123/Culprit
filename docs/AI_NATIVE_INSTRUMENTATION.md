# Running the Culprit MCP server

This is the copyable guide for running `mcp_server/` — the local, stdio
MCP server exposing this Culprit install's own engineering memory (Phase
21's postmortems/decisions/AI change records, Phase 22's invariant
violations, Phase 23's incident links) as four read-only tools a coding
agent can call before making a change — and registering it in a Claude
Code session. It assumes nothing beyond a running Culprit install (local
dev or a real deployment) and that install's own database credentials.

## What this is, and isn't

Four tools, all read-only (`readOnlyHint: true`, enforced at the DB
layer too — the `mcp-reader` role this server connects as has `SELECT`
only, no `INSERT`/`UPDATE`/`DELETE` anywhere):

- `culprit_search_memory` — semantic search across postmortems,
  architecture decisions, and AI change records.
- `culprit_file_history` — a file's own AI change history: which commits
  touched it, which Phase 22 invariant violations they caused, which
  Phase 23 incidents they were linked to.
- `culprit_coupled_files` — the declared "must change together" pair
  (Phase 22's `scripts/coupled_files.yaml`) for a given file, if any.
- `culprit_architecture_decisions` — list or search recorded decisions.

Every result is a historical/observed fact this specific repository's
own Culprit install already recorded — never a live static analysis of
your current working tree. `culprit_coupled_files` returning an empty
list means "no coupling is *declared* here," not "nothing depends on
this file" — Phase 22's own registry only has what's been explicitly
added to it. Don't treat an empty result as a green light.

There's no write-capable tool, and won't be — every write path stays
exactly where Phase 21/23 put it (a human-facing endpoint, or the
automatic commit-time hook). This server runs locally, stdio transport,
alongside your own Claude Code session — it isn't a shared network
service, and isn't part of `docker-compose.prod.yml`.

## 1. Configuration

Two environment variables, both required:

- `MCP_READER_DATABASE_URL` — a `postgresql+asyncpg://` connection string
  for the `mcp-reader` role (created by that role's own migration). Fails
  loudly and immediately at startup if unset — a stdio server that
  instead fails obscurely deep inside a tool call, with no clear
  "you forgot to set this" message, is a much worse debugging experience
  for whoever registers it.
- `VOYAGE_API_KEY` — needed by `culprit_search_memory` and
  `culprit_architecture_decisions`'s query-search path (both embed the
  query text via Voyage before searching). `culprit_file_history` and
  `culprit_coupled_files` never need it.

Where to find `MCP_READER_DATABASE_URL`:

- **Local dev:** `api/.env`'s own `MCP_READER_DATABASE_URL` (generated
  once, by hand, the same way every other role password in that file
  was — see that file's own comments for the other roles' precedent).
- **A real install:** `infra/.env.prod`'s `MCP_READER_DATABASE_URL`,
  generated by `scripts/bootstrap_env.py` (`just quickstart` or
  `just bootstrap-env`) alongside every other role password.

## 2. Running it locally

From the repo root (not `cd mcp_server &&` — `mcp_server/` is a *flat*
package, `pyproject.toml` sits beside `__init__.py`, not one level above
it the way `api/app` or `worker/app` do, so `python -m mcp_server` needs
a working directory *above* the package to resolve `import mcp_server`
at all):

```bash
just mcp-server
```

Equivalent, if you'd rather not go through `just`:

```bash
uv run --project mcp_server python -m mcp_server
```

This blocks, talking JSON-RPC over stdio — it's meant to be launched by
an MCP client (Claude Code), not run standalone in a terminal you're
watching. `Ctrl-C` to stop it.

## 3. Registering it in Claude Code

Claude Code reads MCP server definitions from a `.mcp.json` file (project
root) or via `claude mcp add`. Either way, the server needs its own
environment — `MCP_READER_DATABASE_URL` and `VOYAGE_API_KEY` won't be
inherited from your shell unless you pass them through explicitly.

**Via the CLI** (writes `.mcp.json` for you):

```bash
claude mcp add culprit -- uv run --project mcp_server python -m mcp_server
```

Run this from the repo root, same reasoning as step 2. If your shell
session already has `MCP_READER_DATABASE_URL`/`VOYAGE_API_KEY` exported
(e.g. you've `source`d `api/.env`), the subprocess Claude Code spawns
inherits them; otherwise set them in `.mcp.json` directly:

```json
{
  "mcpServers": {
    "culprit": {
      "command": "uv",
      "args": ["run", "--project", "mcp_server", "python", "-m", "mcp_server"],
      "cwd": "/absolute/path/to/this/repo",
      "env": {
        "MCP_READER_DATABASE_URL": "postgresql+asyncpg://mcp-reader:<password>@localhost:5432/signalstack",
        "VOYAGE_API_KEY": "<your key>"
      }
    }
  }
}
```

After registering, start a new Claude Code session (or reconnect) in
this repo — the four `culprit_*` tools should be available. Verify with
a real question, not just that the tools show up: ask "has
`<some file with real AI change history>` caused problems before?" and
confirm the answer is grounded in an actual `culprit_file_history` call,
not a guess.

## 4. Pointing this at a different install

Nothing about `mcp_server/` is tied to *this* repo's own database beyond
`MCP_READER_DATABASE_URL` — point it at a teammate's deployed Culprit
instead of your own local dev database by changing that one value (and
using that install's own `VOYAGE_API_KEY`, since embeddings must be
generated with the same model/key family the target database's vectors
were written with). There's no separate "which Culprit am I talking to"
concept beyond the connection string.
